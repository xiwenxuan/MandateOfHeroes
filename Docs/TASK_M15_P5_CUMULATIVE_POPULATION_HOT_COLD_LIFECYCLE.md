# M15-P5 任务书：累计永久人物容量、冷热档案与长期增长压力原型

## 一、任务定位

本任务承接M15-P4的100万人分区二进制证据，并落实新的正式人口容量口径：史料人口只
用于参考与相对分布；实际开局按玩家选择缩尺；正式性能目标是单局累计约5,000万永久
人物，而不是开局或同时在世5,000万人。

P5仍是与正式V6存档隔离的独立压力原型。本任务建立可计算的容量合同，验证在世热集、
死亡冷档案、永久人物核心和断点续跑的长期增长行为，但不升级存档版本、不接入Unity
运行时，也不宣称累计5,000万已经通过。

## 二、口径合同

容量模型必须分别记录：

```text
HistoricalReferencePopulation
PopulationScaleBasisPoints
InitialLivingPopulation
CurrentLivingPopulation
PeakLivingPopulation
CumulativePersonCount
DeceasedColdArchiveCount
ProjectionYears
ProjectedBirths
ProjectedDeaths
ProjectedCumulativePersonCount
OfficialSupportedCumulativeTarget
HardwareBudget
HardwarePressure
```

- `HistoricalReferencePopulation`只用于显示与缩尺，不直接生成同量人物；
- `CumulativePersonCount`包含全部在世人物和死亡冷档案，是最终容量指标；
- “预计长期累计人物”必须带明确`ProjectionYears`，不得对260年后的无限发展给出无期限
  单一数字；
- 容量估计使用整数和明确舍入规则，相同输入必须得到相同结果；
- 接近或超过累计5,000万只产生警告或超出保证标记，不阻止出生，不删除、合并或重随机
  永久人物。

## 三、冷热档案原型

独立原型至少保存：

1. 追加式永久人物核心：稳定人物ID、父母、家户、出生时间、出生地区与性别；
2. 在世热索引：仅保存当前在世人物及其下一次生命周期调度信息；
3. 死亡冷档案：保存人物ID、死亡时间和死亡原因，并能与永久核心合并查询；
4. 状态清单：保存当前日、累计人物、在世峰值、出生、死亡、格式版本和确定性参数；
5. 检查点摘要：对永久核心、热索引和冷档案分别计算摘要，恢复后必须一致。

冷热分层只改变加载与访问成本。死亡不删除人物核心，热索引也不能成为永久身份来源。

## 四、长期增长压力负载

P5使用明确标记的确定性技术压力负载：保持受控在世热集，通过顺序死亡与出生替换持续
增加累计永久人物。该负载用于验证存储增长、冷档案、查询、检查点和恢复，不代表东汉
历史生育率、死亡率或人口曲线。

压力阶梯：

1. 自测试与1万累计冒烟；
2. 累计100万永久人物；
3. 从同一检查点续跑到累计500万；
4. 从同一检查点续跑到累计1000万。

冷热长期增长累计5000万留在后续正式压力验收；本任务第十一节另测全部在世的基础上界。
每个阶梯使用独立外部进程和不超过300秒的硬超时；
工具必须定期写入进度，超时后保留阶段、PID、日志和结果。续跑只能读取上一阶梯清单，
不得重新生成、覆盖或重随机既有人物。

## 五、查询与不变量

每个阶梯至少验证：

- 永久人物ID从1单调增长到`CumulativePersonCount`，无重复、无缺口；
- `CumulativePersonCount = InitialLivingPopulation + TotalBirths`；
- `CurrentLivingPopulation = CumulativePersonCount - TotalDeaths`；
- `DeceasedColdArchiveCount = TotalDeaths`；
- `PeakLivingPopulation >= CurrentLivingPopulation`；
- 死者能够通过ID读取永久核心、父母、家户、出生和死亡事实；
- 在世人物能够通过热索引读取，且不出现在死亡冷档案；
- 连续运行与分段续跑在同一目标处产生相同摘要；
- 超过正式目标的容量估计仍允许出生，只返回超出性能保证状态。

## 六、实现边界

- 工具位于`Tools/PopulationBenchmark`，不得让`Mandate.Domain`依赖候选物理格式；
- 原型数据只写入被忽略的`tmp/m15-p5`目录；仓库只保留任务书、工具、复现入口和体积
  可控的汇总报告；
- 不修改V6世界快照、`WorldState.People`、场景、程序集或发布依赖；
- 不实现创建世界UI、自动硬件检测、历史人口一比一生成或正式V7迁移；
- 不通过统计人口代替永久人物，也不因关注层级或性能压力删除人物。

## 八、验收条件

1. 容量估计区分史料参考、开局在世、预计累计和硬件压力，并要求明确推演年限；
2. 自测试覆盖缩尺、确定性、边界警告、超过目标继续出生、冷热守恒和续跑等价；
3. 100万、500万、1000万阶梯均有机器可读结果，或对失败阶梯保留明确负面证据；
4. 通过阶梯完成永久核心、热索引、冷档案、清单、摘要、查询和恢复校验；
5. 没有修改V6存档或正式Unity运行时人口路线；
6. 全工程编译、核心测试、受控Unity测试、`git diff --check`和范围审阅分别有明确结果。

## 九、完成定义

只有任务书、代码、自测试、压力证据、汇总报告和项目级验证全部形成后，P5才可标记完成。
P5冷热阶段通过只表示累计1000万独立冷热档案原型取得证据；第十一节补充验证5000万
全部在世基础核心与紧凑索引。两者都不能外推完整游戏负载，也不能把候选物理格式自动
视为正式存档方案。

## 十一、全热集补充矩阵

初次P5只验证了“累计人物增长、在世热集保持10万”的冷热分层，不能回答极端情况下
全部累计人物仍然在世的容量上界。补充任务必须验证：

```text
CurrentLivingPopulation = CumulativePersonCount
DeceasedColdArchiveCount = 0
```

测试阶梯固定为累计/在世100万、500万、1000万、1500万、2000万、2500万、3000万、
3500万、4000万、4500万和5000万。每一级同时验证：

1. 追加式永久核心和全量在世热索引能够断点续写、恢复和按ID查询；
2. 紧凑常驻热索引尝试把全部人物核心与下一调度日载入内存；
3. 记录生成、追加、常驻加载、峰值工作集、磁盘体积和摘要；
4. 内存不足、超时或其他容量失败必须保留为负面证据，不能降低人数后宣称通过；
5. “全部活着”只表示所有人物拥有在世核心和调度索引，不表示逐人运行完整AI、
   `GameObject`、动画、寻路或逐帧行为；
6. 每个矩阵单元仍由独立进程运行，受300秒硬超时约束；后一级只从已提交清单续写，
   不重新随机或覆盖前一级人物。

补充交付物：

- `Tools/PopulationBenchmark/PopulationAllHot.cs`；
- `Tools/Run-PopulationAllHotSafe.ps1`；
- 十一级机器可读矩阵证据；
- 本任务报告中的全热集结论修订。

在全热集矩阵完成前，P5不得再以“累计1000万冷热档案通过”推定在世峰值容量。
