# MandateOfHeroes 项目专属 Unity 开发 Skill 建设任务书

## 一、文档目的

本任务用于建设一个面向 `MandateOfHeroes` 的项目专属 Codex Skill，使后续功能开发、缺陷修复、重构、测试和交付遵循同一套流程。

Skill 暂定名称为 `mandate-unity-development`。它负责提供项目知识、执行顺序、工具入口和验收模板；`AGENTS.md` 仍是项目最高优先级的执行规则。两者发生冲突时，以 `AGENTS.md` 和用户当轮明确要求为准。

本任务书既是 Skill 的建设清单，也是建成后的使用和维护规则。

## 二、建设目标

1. 让 Codex 在接到项目开发任务时，能快速找到正确的模块、文档和测试入口。
2. 固化“理解需求—检查现状—实施—编译—核心测试—受控 Unity 测试—交付”的开发闭环。
3. 避免 Unity 前台驻留、项目锁冲突、测试无限等待和无结果宣称通过。
4. 统一新增功能、修复缺陷、调整数据、修改存档和编辑器集成任务的验收标准。
5. 让任务结束时留下可审计的变更范围、测试证据、限制和后续建议。
6. 通过渐进式加载控制上下文体积，只在任务需要时读取对应领域资料。

## 三、适用范围

下列请求应触发或明确指定此 Skill：

- 在 `MandateOfHeroes` 中新增、修改或重构 Unity/C# 功能；
- 修改领域模型、世界模拟、战斗、人物、地图、任务、经济或存档系统；
- 修改 ScriptableObject、场景、Prefab、序列化或编辑器集成；
- 诊断编译错误、核心测试失败、Unity 导入或测试失败；
- 为某个里程碑编写实现方案、验收清单或完成记录；
- 在提交前执行项目规定的验证流程。

下列工作不应仅依赖本 Skill：

- 纯美术生成应配合 `imagegen`；
- 数值表或批量数据分析应配合电子表格 Skill；
- PR、CI 和代码审查工作应配合 GitHub Skills；
- 与本项目无关的通用 Unity 问题不强制触发本 Skill。

## 四、交付物

建议将 Skill 建设为以下结构：

```text
mandate-unity-development/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   └── verify-project.ps1
└── references/
    ├── architecture.md
    ├── testing.md
    ├── persistence.md
    ├── content-and-data.md
    └── delivery-template.md
```

各文件职责如下：

### 4.1 `SKILL.md`

只保留每次开发都必须执行的核心流程：

- 项目识别与触发条件；
- 规则优先级；
- 开工检查；
- 修改原则；
- 验证顺序；
- Unity 安全运行约束；
- 交付报告要求；
- 各参考文档的读取条件。

正文应简洁，原则上不超过 500 行。详细架构和领域资料放入 `references/`，避免每次触发都加载全部项目知识。

### 4.2 `agents/openai.yaml`

提供 Skill 在界面中的显示名称、简短说明和默认提示词。其内容必须与 `SKILL.md` 保持一致，不得承诺 Skill 实际不具备的能力。

### 4.3 `scripts/verify-project.ps1`

提供统一验证入口，按顺序执行：

1. `git diff --check`；
2. 全工程编译；
3. `Tools/CoreTestRunner.cs` 对应的快速核心测试；
4. 在明确允许且环境无锁冲突时，通过 `Tools/Run-UnityTestsSafe.ps1` 执行受控 Unity 测试；
5. 汇总每一步的命令、退出码、日志路径和结果路径。

脚本不得绕过 `AGENTS.md`，不得直接以前台方式启动 Unity。默认硬超时为 300 秒；如需延长，必须先取得用户同意。

### 4.4 `references/architecture.md`

记录项目模块边界、主要程序集、依赖方向和关键目录，例如：

- `Mandate.Domain`；
- `Mandate.Simulation`；
- `Mandate.Persistence`；
- `Mandate.Presentation`；
- `Assets/_Project` 下的领域目录；
- 测试代码与生产代码的对应关系。

只记录稳定且能帮助定位代码的内容，不复制大段设计文档。

### 4.5 `references/testing.md`

记录：

- 编译命令和预期产物；
- 核心测试入口；
- Unity 测试安全入口；
- Unity 进程与项目锁检查；
- 日志、结果文件和超时处理；
- 各类修改至少需要覆盖的测试层级；
- “通过”“失败”“阻塞”“未执行”的判定规则。

### 4.6 `references/persistence.md`

记录存档 DTO、版本迁移、确定性要求和兼容策略。任何涉及存档结构、随机数、时间推进或世界状态的任务都必须读取此文件。

### 4.7 `references/content-and-data.md`

记录 ScriptableObject、静态配置、历史内容、授权信息和数据校验要求。任何新增人物、城市、事件、资源或美术数据的任务都必须读取此文件。

### 4.8 `references/delivery-template.md`

提供统一完成记录模板，至少包含：

- 任务目标；
- 实际变更；
- 涉及文件；
- 编译结果；
- 核心测试结果；
- Unity 测试结果或阻塞证据；
- 已知限制；
- 后续建议。

## 五、必须固化的开发流程

### 5.1 开工检查

1. 读取仓库根目录的 `AGENTS.md`。
2. 阅读当前任务直接关联的 `Docs/` 设计或里程碑文档。
3. 检查工作区状态，识别用户已有修改，不覆盖或回退无关变更。
4. 搜索现有实现和测试，优先扩展已有抽象，避免创建重复系统。
5. 明确任务边界、验收条件和可能影响的存档或序列化版本。
6. 若上一轮外部工具调用被中断，先检查由该任务启动且已超时的遗留进程。

### 5.2 实施规则

1. 领域规则优先放在可脱离 Unity 运行的纯 C# 层。
2. 表现层不得成为核心状态的唯一来源。
3. 随机行为必须使用项目统一的确定性随机机制。
4. 存档对象使用独立 DTO，不直接序列化复杂运行时对象。
5. 修改现有存档结构时必须提供版本迁移或明确的兼容处理。
6. 新增行为必须增加对应测试；修复缺陷时优先增加可复现该缺陷的回归测试。
7. 不引入来源不明或许可证不兼容的第三方素材和代码。
8. 只修改当前任务范围内的文件，不顺带进行无关格式化或大规模重构。

### 5.3 验证顺序

每轮开发必须依次执行：

1. 全工程编译；
2. 快速核心测试；
3. 一次受控 Unity 测试；
4. 交付前执行 `git diff --check` 并审阅实际差异。

前一步失败时，先定位并修复，不得跳过后直接宣称任务完成。文档专属修改可不启动 Unity，但必须明确记录“未运行：仅文档变更”，并执行适合文档的差异检查。

### 5.4 Unity 安全规则

1. 禁止前台直接运行 Unity 或其他可能长期驻留的工具。
2. 启动 Unity 批处理前必须检查现有 Unity 进程。
3. 若用户的 Unity 编辑器已打开，应停止批处理并报告项目锁冲突，不得关闭用户进程。
4. Unity 测试只能通过 `Tools/Run-UnityTestsSafe.ps1` 启动。
5. 长任务必须在后台运行，并以不超过 5 秒的间隔轮询。
6. 全程保留进程 ID、日志路径和结果路径。
7. 默认硬超时为 300 秒；到时主动终止本次启动的进程树并报告日志尾部。
8. 未取得测试结果文件或明确运行汇总，不得声称 Unity 测试通过。

## 六、不同任务类型的最低验收要求

| 任务类型 | 编译 | 核心测试 | Unity 测试 | 额外要求 |
| --- | --- | --- | --- | --- |
| 纯领域逻辑 | 必须 | 必须 | 最终至少一次 | 确定性和边界条件 |
| 存档或 DTO | 必须 | 必须 | 必须 | 旧版本迁移、往返一致性 |
| ScriptableObject 或序列化 | 必须 | 相关测试 | 必须 | 导入与字段持久化 |
| 场景、Prefab、UI | 必须 | 相关测试 | 必须 | 场景加载与引用完整性 |
| 缺陷修复 | 必须 | 必须 | 视影响范围 | 回归测试先复现后修复 |
| 重构 | 必须 | 必须 | 最终至少一次 | 行为保持不变 |
| 纯文档 | 不要求 | 不要求 | 不要求 | `git diff --check`、内容复核 |

Unity 测试因编辑器锁定或环境问题无法运行时，状态只能记为“阻塞”或“未执行”，并附进程检查、日志或脚本输出作为证据。

## 八、后期使用方法

### 8.1 显式调用

在开发请求中直接指定 Skill，示例：

```text
使用 $mandate-unity-development，为人物教育系统增加师徒关系中断规则，
完成实现、回归测试和交付记录。
```

```text
使用 $mandate-unity-development，诊断 V5 存档读取后军队服役记录不一致的问题。
只诊断并给出证据，不要修改代码。
```

```text
使用 $mandate-unity-development，完成 TASK_M11。
严格按编译、核心测试、受控 Unity 测试的顺序验收。
```

### 8.2 自动触发

安装后，当请求明确涉及 `MandateOfHeroes` 的 Unity/C# 开发、测试、存档或里程碑验收时，Codex 应根据 Skill 描述自动选择它。重要任务仍建议显式写出 Skill 名称，避免触发歧义。

### 8.3 推荐任务输入格式

每次使用时尽量提供：

```text
目标：
范围：
不做什么：
验收条件：
是否允许修改存档版本：
是否需要提交：
```

信息不完整但风险较低时，Codex可依据现有设计文档作最小假设并明确记录。涉及存档破坏、架构方向变化、关闭用户进程或扩大任务范围时，必须先获得用户授权。

### 8.4 预期输出

Skill 执行后的最终报告应简洁说明：

1. 已实现或已诊断的结果；
2. 关键修改文件；
3. 编译、核心测试和 Unity 测试的真实状态；
4. 阻塞证据或未执行原因；
5. 已知限制和合理的下一步。

## 九、维护规则

1. `AGENTS.md` 的强制规则发生变化时，必须同步检查 Skill。
2. 程序集、目录、测试脚本或存档版本变化时，更新对应参考文件。
3. Skill 正文只保存稳定流程，频繁变化的信息放入参考文件。
4. 不在多个文件中重复维护同一规则；必须指定唯一事实来源。
5. 每次修改 Skill 后运行 `quick_validate.py`。
6. 修改脚本后必须实际运行代表性场景，不得只做静态检查。
7. 连续两次真实任务出现同类误操作时，应将防护加入 Skill 或确定性脚本。
8. 连续三个月未使用的可选内容应评估删除，防止 Skill 膨胀。
9. 每个里程碑结束时检查架构索引、测试入口和交付模板是否仍准确。
10. Skill 不保存密钥、账号、机器专属绝对路径或不可公开的素材。

## 十一、禁止事项

- 禁止让 Skill 绕过或弱化 `AGENTS.md`；
- 禁止直接关闭用户已打开的 Unity 编辑器；
- 禁止以前台方式启动可能长期驻留的 Unity、构建或测试进程；
- 禁止把“编译通过”写成“全部测试通过”；
