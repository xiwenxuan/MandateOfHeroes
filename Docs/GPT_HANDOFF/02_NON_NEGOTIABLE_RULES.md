# GPT 提案必须遵守的项目规则

> 摘要日期：2026-08-09
> 若本文与仓库 `AGENTS.md`、系统总纲或正式领域设计冲突，以仓库权威文件为准。

## 1. 状态必须说清楚

项目只使用四类系统状态：

| 状态 | 含义 |
|---|---|
| 已有原型 | 已能在Unity原型中操作并观察结果 |
| 已有底座 | 关键数据或最小闭环已有代码，但内容、规模或表现不完整 |
| 已定方案 | 设计已确认，尚未形成正式可玩实现 |
| 待研究 | 方向存在，但数据、性能或实现方法仍需验证 |

“用户接受了建议”“文档写完”“任务书建立”“代码编译”“自动测试通过”“人工试玩认可”是不同事实。

## 2. 一个世界、一本事实账

人物、家庭、土地、资源、设施、产品、库存、财政、职位、军队和事件只能有一份权威状态。
地图缩放、进入城镇、点击建筑、切换视角和进入战斗不能创建第二套事实。

世界只在创世时初始化一次。运行后所有变化必须来自行动、时间和世界事务。

## 3. 永久人物

- 每个人出生时立即拥有永久唯一身份；
- 冷存、降格和降低AI频率只减少计算与表现，不删除人物；
- 不得合并、替代、重随机或把人物重新变成无名人口数字；
- 死亡人物仍保留身份、血缘、履历和世界影响；
- 关注只改变信息和演出精度，不改变事实。

正式长期目标是单局累计约5000万永久人物，不表示当前已经通过5000万完整游戏负载。

## 4. 守恒与可追溯

- 人口变化来自出生、死亡、迁徙、服役等真实事件；
- 兵员来自永久人物，伤亡、俘虏、逃亡和复员必须回写个人；
- 产品、军粮和药材来自生产、交易或转移，可发生有原因的损耗；
- 财政必须有付款方、收款方或明确消耗；
- 劫掠不能创造物资，战争破坏必须改变真实库存和设施。

“守恒”不表示没有损耗，而是损耗必须有来源、原因和审计记录。

## 5. 有限认知

玩家和AI只能使用本人观察、记忆、合法文档、家族档案、职位授权档案和已经取得的情报。
未知矿脉、库存、价格、道路、敌军或布防不能因为切换专题视图自动显示。

离任后不再自动获得原组织的最新资料；抄录和传递信息需要具体人物、载体、时间、地点与权限。

## 6. 数据驱动与稳定ID

作物、产品、配方、设施、模块、技艺、词条、科技、装备、兵种、阵法、任务、事件、职位和爵位等
可持续扩展内容应使用稳定命名空间ID和数据定义。增加普通内容或MOD内容不应要求升级存档结构。

缺失内容ID不得静默改指、删除或重新随机。只有生命周期、协议状态等真正封闭集合适合枚举。

## 7. 确定性与存档

- 随机行为使用稳定ID、明确世界时间/动作坐标和命名随机流；
- 相同内容、种子和输入应得到相同结果；
- 存档结构变化必须顺序迁移；
- 新旧存档要进行往返测试与不变量校验；
- 表现层或GPT文本不能成为唯一规则来源。

## 8. Cell与Facility

- HanWorldV1沿用2000米Cell，不擅自改回无尺度地图；
- 一个Cell同一时刻只有一个Owner；
- 一个Cell最多一个基础Facility和一支独立Force，二者为不同占用槽；
- 大城市、宫城、庄园、矿区和防线由多Cell、多Facility组成；
- Facility内部不另建第二套SubCell世界账；
- 小型内部功能作为Module，具有独立人员、库存、损毁或战略意义的功能应成为Facility；
- 设施目录是数据内容，不是固定枚举。

## 9. 人物时间与劳动

同一人物在同一世界时段只能承担一项主要耗时活动。生产、学习、旅行、服役、治疗和休息不能
同时贡献多份时间。职位、关系、产权和被动状态可以并存。

本地正常通勤可以包含在工作活动中；跨区域旅行、赴任、商旅和行军必须真实耗时。

## 10. 权限与自动化

- 身份决定玩法入口，职位和授权决定合法操作范围；
- 官职、军职、爵位、产权和实际兵权分别保存；
- 玩家和AI共用相同命令、权限、知识、资源和时间规则；
- 委任必须形成真实目标、受任者、预算、期限、红线、报告和领域命令；
- 自动化不得使用“托管加成”凭空产生物资或结果；
- 玩家可以在合法层级接管或交还控制，进度和世界事实不重置。

## 11. 架构边界

```text
Mandate.Domain       纯C#世界状态、不变量、稳定身份与确定性规则
Mandate.Simulation   时间推进、跨实体行为、命令与事务编排
Mandate.Persistence  存档、迁移、分区、检查点与兼容
Mandate.Presentation Unity界面、输入、场景、动画与视觉表现
```

核心世界事实不得只存在于Unity场景、GameObject、MonoBehaviour或UI中；Domain不得反向依赖表现层。

## 12. 内容与许可证

- 参考商业游戏只能吸收抽象设计思想；
- 不复制其代码、地图、美术、音乐、文本、UI、任务和数值表；
- 外部代码、数据和素材必须先确认兼容许可证并记录来源；
- 不清楚许可证时，只做独立重写和原创内容。

## 13. GPT 输出要求

每次提案应明确分成：

1. 已有项目规则；
2. 从资料推断出的内容；
3. GPT新增建议；
4. 需要用户确认的决策；
5. 可能冲突的旧规则；
6. 预计影响的系统、文档、存档、性能与玩家体验；
7. 当前只是讨论、已接受方案、任务书还是已实现事实。
