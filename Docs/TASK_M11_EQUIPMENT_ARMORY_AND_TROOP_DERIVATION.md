# M11 任务书：人物装备、军械库与兵种派生

> 兼容说明：本文形成时正式存档仍为V5，因此原方案曾把装备扩展规划为
> V5→V6。M14已经使用V6保存村庄与家户事实；本任务尚未实施，后续执行不得复用V6，
> 必须从届时当前版本顺序升级到下一版本，并重新核对全部迁移测试。

## 一、任务定位

本任务是《统一战斗、军团与战争权限系统设计》的 P2 里程碑，也是
`mandate-unity-development` 项目专属 Skill 建成后的第一个正式开发任务。

M10 已经回答了“军队中的人是谁、属于哪个编制、谁有权下令”；M11 接着回答：

```text
每名服役人物拿着什么
+ 军队还库存什么
+ 装备是否齐整、是否损坏
+ 人物能力和现有装备适合担任什么兵种
+ 战斗后装备去了哪里
```

任务重点是建立可守恒、可存档、可审计的装备事实链，不追求一次完成复杂战术战斗。

## 二、开发目标

1. 给真实服役人物发放真实装备，不再用“军队默认自带武器”代替。
2. 为每支军队建立聚合军械库，区分可用、损坏和已发放装备。
3. 依据人物能力、职责和实际装备派生基础兵种，而不是让兵种脱离人物存在。
4. 计算军队与基层编制的装备齐整度。
5. 将装备齐整度接入现有军团战斗力计算。
6. 让战斗产生装备损坏、遗失和有限缴获，并保持装备守恒。
7. 将装备定义、库存、发放和事务写入实施后的新版本存档。
8. 在开发观察台展示军械库存、兵种构成、齐整度和近期装备事务。

## 三、核心设计原则

### 3.1 一本装备账

```text
期末可追踪装备
= 期初装备
+ 获得
+ 缴获
+ 归还
- 发放
- 遗失
- 永久损毁
```

“发放”只改变装备所在位置，不改变世界装备总量。军械库库存和人物携行装备不得重复计数。

### 3.2 兵种由事实派生

兵种由以下信息共同决定：

```text
人物职责
+ 人物能力
+ 已发放装备
+ 军队训练状态
= 当前可担任兵种
```

没有弓和箭的士卒不能被计算为弓兵；只有盾而没有近战武器也不能成为完整刀盾兵。

### 3.3 制式装备不逐件实例化

本阶段不为每一把普通长矛创建独立对象。军械库使用按种类聚合的库存；
发放到重要人物或具体服役人物时，记录“装备种类、数量和平均状态”。

名器、宝物和唯一装备留待后续独立实例系统。

### 3.4 与真实服役账绑定

- 只有存在有效 `MilitaryServiceState` 的人物可以领取军用装备；
- 发放记录必须指向具体人物和军队；
- 退役、被俘、逃亡或死亡后的装备必须进入归还、遗失或缴获流程；
- 不允许删除服役记录来隐式删除装备。

## 四、领域对象

### 4.1 `MilitaryEquipmentDefinitionState`

建议字段：

- `Id`；
- `DisplayName`；
- `Kind`；
- `Slot`；
- `UnitWeight`；
- `MaximumConditionBasisPoints`；
- `MeleePowerBasisPoints`；
- `RangedPowerBasisPoints`；
- `ProtectionBasisPoints`；
- `RequiredStrengthBasisPoints`；
- `RequiredDexterityBasisPoints`；
- `AmmunitionEquipmentId`；
- `IsUnique`，本阶段固定为 `false`。

原型装备：

- 环首刀；
- 木盾；
- 长矛；
- 角弓；
- 箭束；
- 札甲。

### 4.2 `MilitaryArmoryStockState`

建议字段：

- `Id`；
- `ArmyId`；
- `EquipmentDefinitionId`；
- `AvailableQuantity`；
- `DamagedQuantity`；
- `AverageConditionBasisPoints`；
- `OpeningQuantity`。

同一军队与装备种类只能存在一条库存记录。

### 4.3 `MilitaryEquipmentIssueState`

建议字段：

- `Id`；
- `MilitaryServiceId`；
- `PersonId`；
- `ArmyId`；
- `EquipmentDefinitionId`；
- `Quantity`；
- `ConditionBasisPoints`；
- `IssuedDay`；
- `LastChangedDay`。

同一人物可以持有互补装备，例如环首刀、木盾和札甲；同一槽位不得出现不兼容重复发放。

### 4.4 `MilitaryEquipmentTransactionState`

事务类型至少包括：

- 期初入库；
- 发放；
- 归还；
- 损坏；
- 修复；
- 遗失；
- 缴获；
- 军队间调拨。

建议字段：

- `Id`；
- `Day`；
- `Type`；
- `EquipmentDefinitionId`；
- `Quantity`；
- `FromArmyId`；
- `ToArmyId`；
- `MilitaryServiceId`；
- `BattleId`；
- `Summary`。

### 4.5 派生结果

基础兵种枚举：

- 无完整武装；
- 刀盾兵；
- 长矛兵；
- 弓兵；
- 近战杂兵；
- 军官/指挥人员；
- 军医与军需等非战斗职责。

派生结果原则上由查询系统实时计算，不作为第二份权威状态长期保存。

## 五、装备与兵种规则

### 5.1 发放优先级

建议按稳定顺序发放：

1. 主将和军官的基本自卫装备；
2. 已具备对应能力的弓兵候选；
3. 长矛兵候选；
4. 刀盾兵候选；
5. 普通士卒的剩余装备；
6. 军医、军需官和信使只领取职责允许的装备。

所有排序必须使用稳定 ID 和确定性规则，不能依赖当前列表偶然顺序。

### 5.2 基础兵种派生

#### 刀盾兵

- 持有近战刀剑；
- 持有盾；
- 身体与力量满足最低要求；
- 不是军医等排除职责。

#### 长矛兵

- 持有长矛；
- 力量、体质或军略能力满足最低要求；
- 没有被更高优先级职责占用。

#### 弓兵

- 持有弓；
- 持有至少一束箭；
- 灵巧和感知满足最低要求。

#### 无完整武装

- 没有形成任何完整装备组合；
- 仍是具体服役人物，但战斗贡献显著降低。

### 5.3 齐整度

每个战斗服役人物根据职责拥有一个最低装备需求。基层编制齐整度建议为：

```text
满足最低需求的可战成员数
÷ 可战成员总数
```

军队齐整度由各基层编制按可战人数加权。军医、军需官等非战斗职责不纳入普通兵种齐整度分母。

### 5.4 装备状态

- `8,000–10,000`：良好；
- `5,000–7,999`：可用但性能下降；
- `1–4,999`：损坏，不能正常发放；
- `0`：永久损毁并从可追踪装备总量扣除。

## 六、原型初始化

三支 80 人缩尺军队使用不同装备结构，以便验证兵种差异：

### 冀州官军前锋

- 装备较齐整；
- 刀盾与长矛比例均衡；
- 少量弓兵；
- 军官护甲较好。

### 幽州援军

- 弓与长矛较多；
- 盾和护甲略少；
- 体现北方边军的远射和长兵倾向，但不照搬商业游戏数值。

### 广宗黄巾主力

- 人数相同但装备齐整度最低；
- 大量近战杂兵和无完整武装人员；
- 少量缴获的官军制式装备；
- 通过士气与人数以外的因素体现战力差异。

全部期初装备必须写入“期初入库”事务，然后再通过发放事务进入人物携行状态。

## 七、系统接入

### 7.1 原型世界

- 在真实服役初始化完成后初始化军械；
- 装备定义 ID、库存顺序和发放结果保持确定性；
- 初始化结束后执行人物、服役、库存、发放和装备总量联合校验。

### 7.2 战斗力

现有战斗力计算增加装备齐整度因子：

```text
战斗力
= 现有兵力、士气和训练结果
× 装备齐整度修正
× 兵种适配修正
```

本任务只加入温和修正，避免装备系统上线后完全破坏既有战斗平衡。

### 7.3 战后装备

- 伤员默认保留装备；
- 阵亡者的装备按确定性比例分为可回收、损坏、遗失；
- 逃亡者默认带走个人携行装备，记录为遗失；
- 胜方可以缴获败方一部分可回收装备；
- 缴获进入胜方军械库，不直接自动发放；
- 每项变化都必须写入装备事务并关联战斗记录。

### 7.4 医疗、退役与归队

- 医疗只改变服役和健康状态，不自动修复装备；
- 康复者保留仍可用的原装备；
- 后续退役接口应先归还可归还装备；
- 本阶段不实现工匠修理，但保留损坏库存和修复事务类型。

### 7.5 开发观察台

增加：

- 各军军械库可用/损坏数量；
- 各军刀盾、长矛、弓兵、杂兵和未武装人数；
- 各基层编制装备齐整度；
- 当前选中服役人物的装备；
- 最近装备发放、损坏、遗失和缴获事务；
- 战斗前后装备总量审计。

## 八、存档与迁移

实施时世界存档由届时当前版本升级至下一顺序版本，新增：

- `MilitaryEquipmentInitialized`；
- `MilitaryEquipmentDefinitions`；
- `MilitaryArmoryStocks`；
- `MilitaryEquipmentIssues`；
- `MilitaryEquipmentTransactions`。

从届时当前版本迁移的策略：

- 新集合初始化为空；
- `MilitaryEquipmentInitialized = false`；
- 保留旧版本的真实服役、兵力、伤亡和军令；
- 不根据旧战斗历史倒推或伪造装备；
- 旧存档继续使用无装备兼容战斗修正，直到显式执行装备初始化或开始新世界。

必须继续支持V1至新版本的连续迁移路径。不得覆盖M14已经定义的V6村庄、家户和
永久人物字段。

## 九、校验规则

至少校验：

1. 所有装备定义、库存、发放和事务 ID 唯一且稳定。
2. 库存必须引用有效军队和装备定义。
3. 发放必须引用有效服役记录、人物、军队和装备定义。
4. 发放人物、服役记录和军队必须相互一致。
5. 数量不得为负，状态值必须在合法范围。
6. 同一人物不得持有互斥槽位的重复装备。
7. 弹药发放必须能引用对应远程武器定义。
8. `可用库存 + 损坏库存 + 已发放 + 永久损毁` 与期初及事务净变化一致。
9. 装备齐整度必须能从人物发放记录重新计算。
10. 未初始化兼容模式不得伪造装备记录。
11. 战斗关联事务必须引用有效战斗记录。
12. 缴获事务的双方军队不能相同。

## 十、测试任务

至少新增以下核心测试：

1. 原型世界创建六种装备定义。
2. 三支军队都建立军械库存和期初事务。
3. 发放不会创造或删除装备。
4. 每条发放记录都绑定具体服役人物。
5. 相同种子产生相同发放与兵种派生。
6. 刀盾、长矛和弓兵只在装备组合完整时派生。
7. 能力不足时即使有装备也不会派生为对应专业兵种。
8. 非战斗职责不会计入普通兵种齐整度。
9. 军队齐整度等于基层编制加权结果。
10. 装备齐整度能够影响战斗力，但不绕过兵力、士气和训练。
11. 战斗损坏、遗失和缴获均写入事务。
12. 阵亡者装备不会同时留在人物身上和进入库存。
13. 逃亡者携行装备从军队可追踪资产中扣除。
14. 医疗康复不凭空修复装备。
15. 完成本任务后的新版本存档往返保持装备事实一致。
16. 从实施前当前版本迁移后保留服役、村庄和家户数据，且装备处于未初始化兼容状态。
17. V1 至新版本连续迁移通过。
18. 重复发放、负库存、非法引用和守恒篡改被校验拒绝。
19. 既有 M1 至 M10 测试不得回归。

## 十一、界面验收

在开发观察台中应能回答：

- 这支军队有多少可用武器和损坏武器？
- 哪个基层编制最缺装备？
- 每种基础兵种有多少人？
- 某名真实士卒当前持有什么？
- 一场战斗损失和缴获了哪些装备？
- 装备总账是否守恒？

本任务不要求正式装备图标或角色换装美术，文本观察台即可验收。

## 十二、不在本任务范围

- 唯一名器和宝物实例；
- 工匠生产、采购订单和商人承运；
- 装备修理的完整经济流程；
- 数十种细分兵种；
- 骑兵马匹个体化；
- 水战与船只；
- 攻城器械生产；
- 阵法、战法和计谋；
- 局部交战地图；
- 个人战操作；
- 正式装备 UI、美术和动画。

## 十三、执行顺序

1. 使用 `$mandate-unity-development` 开工检查。
2. 审计 M10 服役、战斗、伤亡、存档和观察台实现。
3. 建立领域对象、装备守恒公式和校验。
4. 从实施前当前版本建立到下一版本的顺序迁移。
5. 实现确定性军械初始化、发放和兵种派生。
6. 接入战斗力、战损、遗失和缴获。
7. 接入开发观察台。
8. 补充核心测试和存档测试。
9. 使用 Skill 统一验证脚本依次执行编译、核心测试和受控 Unity 测试。
10. 审阅差异并填写完成记录；未经用户明确授权不提交或推送。
