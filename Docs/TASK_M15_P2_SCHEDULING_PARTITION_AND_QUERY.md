# M15-P2 任务书：调度、分区与查询深化

## 一、任务定位

本任务承接已完成的M15-P0共同合同与M15-P1三候选后端实验，在同一套10,000名永久
人物压力数据上深化到期调度、跨分区引用和生产所需查询。P2验证“世界怎样只处理当前
需要变化的人，并把变化批量回写到具体人物”；不运行10万/100万人正式压力，不选择
正式后端，也不修改V6世界快照。

## 二、实现范围

1. 为三候选增加P2批量人物、家户和事件变更合同；变更进入候选物理目录内的确定性
   追加日志，同时更新可检查点恢复的活动人物视图。
2. 按绝对日1、30、365连续推进，分别形成一日、首月和首年证据；每次只读取尚未完成
   且已到期的队列节点。
3. 对出生、死亡、婚育、迁徙、疾病、服役和职业变化生成确定性结果；出生创建新的永久
   人物ID，死亡只退出日常调度而不删除人物。
4. 每次推进记录队列扫描、到期事件、实际变化人物、家户写回、新事件、加载分区和批量
   写回数量，并校验人口与地点守恒。
5. 在输入上确定性构造少量“人物当前地点与原家户/父母地点不同”的迁徙样本，用于验证
   跨分区父母、家户和组织引用；测试数据继续标记为 `pressure_test_v1`。
6. 增加血缘子女反向查询，以及地点、职业、组织、健康、劳动力状态和可用状态组合查询。
7. 验证分区卸载/加载、全年推进、完整检查点恢复和关注展开前后永久身份及摘要不变。

## 三、调度合同

每个候选按相同顺序执行：

```text
写入P2跨分区数据集
→ 建立初始检查点
→ AdvanceTo(day=1)
→ AdvanceTo(day=30)
→ AdvanceTo(day=365)
→ 血缘、家户、组织与劳动力查询
→ 跨分区卸载/加载及引用解析
→ 关注展开/释放
→ 完整检查点恢复
→ 核对人口、引用、事件和确定性摘要
```

同一到期事件只允许提交一次。新增后续事件必须使用稳定人物ID、绝对日、原因、规则版本
和动作坐标；不能使用系统时间、运行顺序或不稳定哈希。

## 四、守恒与查询证据

P2至少记录：

- 推进前后永久人物总数、存活人数、出生和死亡数；
- 每个时间窗的队列扫描数、到期数、变化人物数、家户数、新事件数和写回数；
- 迁徙前后各地点人口总和不变，死亡不减少永久人物总数；
- 父母、子女、家户成员、组织成员和跨分区引用的解析数量；
- 劳动力查询候选数与结果数，结果必须同时满足地点、职业、健康、劳动力和可用条件；
- 分区往返、关注往返、检查点恢复前后的核心与事件摘要；
- 三种候选之间的最终摘要、人口守恒和时间窗计数一致性。

## 五、物理与架构边界

- P2追加日志是候选实验的一部分，不是正式存档格式；正式物理合并、压缩和迁移由P3证据
  之后的新任务决定。
- 活动视图可以保存已加载人物与重建索引，但不能代替永久物理事实；检查点必须同时保存
  物理候选文件、变更日志和活动视图。
- 不向 `Mandate.Domain`、Unity程序集或发布包加入SQLite、Newtonsoft或基准工具依赖。
- 不生成 `GameObject`、场景角色、逐帧AI或全人口每日遍历。

## 六、验收条件

1. 三后端都以相同种子和相同P2数据集完成1、30、365日连续推进。
2. 每个窗口的扫描数等于实际到期节点数，且不扫描未到期人物或已完成事件。
3. 出生立即获得唯一永久ID并加入具体家户；死亡人物仍可按ID和血缘查询。
4. 人口满足“期末永久人物=期初永久人物+出生”，存活人口满足“期末存活=期初存活+
   出生-死亡”，迁徙前后世界人物总数不变。
5. 具体人物变化与批量写回一一对应，后续事件具有稳定动作坐标。
6. 跨分区人物能够解析家户、父母、子女和组织；分区往返与恢复不破坏引用。
7. 劳动力组合查询不返回死亡、患病、服役、旅行中或已占用人物。
8. 三后端最终摘要、各窗口计数和守恒结果一致；同候选检查点恢复摘要一致。
9. 安全入口保留PID、日志、结果文件、退出码与不超过300秒的硬超时。
10. 全工程编译、核心测试、受控Unity测试、`git diff --check`和差异审阅分别通过。

## 七、明确不包含

- 10万、100万及更高人口压力和正式后端推荐；
- V6升级、正式存档迁移、发布包依赖或数据库部署；
- 完整婚姻配对、真实生育率、疾病模型、服役制度或生产工单；
- 为证明到期调度而逐人每日运行完整AI；
- 把P2测试迁徙和事件结果冒充史料事实。

## 八、完成定义

只有三种候选都形成机器可读P2结果、守恒与摘要一致，并完成项目级验证后，才能称
“M15-P2完成”。下一步仍为P3的10万与100万人正式压力和后端决策报告。
