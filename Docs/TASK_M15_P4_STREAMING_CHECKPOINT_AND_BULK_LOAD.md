# M15-P4 任务书：流式检查点、分区生成与批量装载优化

## 一、任务定位

本任务承接M15-P3“100万人无候选完整通过”的负面证据，修复独立压力工具中的共同内存
复制和关系后端初写瓶颈，然后重新运行10万与100万正式矩阵。任务仍属于候选实验，不修改
V6世界存档、不把数据库依赖接入Unity运行时，也不删减永久人物、家户、父母、事件或查询
事实。

## 二、已证实瓶颈

1. 完整检查点先构造全量对象列表、JSON字符串和字节数组，100万分区二进制因此内存不足；
2. 确定性摘要使用全量`StringBuilder`，在大档位产生额外全量字符串；
3. SQLite与混合候选逐记录创建命令，并在已有二级索引下写入，10万初写超过285秒；
4. 生成器在完成后再次按地点分组，短时间保留额外字典和列表；
5. P3超时只能通过工作目录推定阶段，缺少候选主动写出的阶段标记。

## 三、实施内容

### 3.1 流式持久化合同

- 为候选存储增加流式增量保存、流式完整检查点和文件恢复入口；
- JSON直接写入文件流，不构造全量`string`或`byte[]`；
- 物理候选文件按文件复制进入检查点目录，并用后端与格式清单验证恢复；
- 原P0—P3字节数组合同继续保留，用于既有小规模回归。

### 3.2 流式确定性摘要

- 按稳定ID顺序逐记录写入SHA-256流；
- 摘要字段、分隔符和顺序与P2/P3保持一致；
- 小规模新旧摘要必须一致。

### 3.3 分区生成与内存释放

- 人物生成时直接加入稳定地点分区，取消生成完成后的全量重新分组；
- P4每个候选使用独立进程；初写完成后释放只用于装载的全局列表和分区列表引用；
- 只释放重复容器，不删除、合并、替代或重新随机任何永久人物事实。

### 3.4 SQLite与混合批量装载

- 整个初写使用单一明确事务；
- 复用已准备的参数命令；
- 初写前移除二级索引，提交后统一重建；
- 失败或超时仍保留数据库、阶段、PID、峰值工作集和日志。

### 3.5 阶段证据

候选至少输出并刷新以下阶段：生成完成、批量初写、初始检查点、全年调度、查询、最终增量、
最终检查点、恢复和完成。安全包装器把最后阶段写入外层结果。

## 四、正式矩阵

| 人口档 | SQLite | 分区二进制 | 混合 |
|---|---|---|---|
| 100,000 | 独立进程 | 独立进程 | 独立进程 |
| 1,000,000 | 独立进程 | 独立进程 | 独立进程 |

每个候选预算最多285秒，为编译、证据落盘和终止留出余量；每个外部工具总调用不超过300秒。

## 五、验收条件

1. P0、P1和P2现有合同继续通过，10万已通过摘要与P3一致；
2. 流式检查点恢复前后的核心摘要和事件摘要一致；
3. 通过候选完成日1、30、365调度、守恒、查询、关注、增量、检查点和恢复合同；
4. 六个矩阵单元均有外层机器可读结果，失败/超时具有最后阶段和资源证据；
5. 所有候选保持同一种子、M13输入、时间窗和永久人物字段；
6. 至少一个100万候选通过后，才能建议另建正式后端选择任务；若仍无候选通过，P4以新的
   负面证据完成，不得宣称支持100万；
7. 全工程编译、核心测试、受控Unity测试、`git diff --check`和差异审阅分别通过。

## 六、明确不包含

- V6迁移、V7存档、正式运行时数据库适配器或发布依赖；
- 1000万和累计5000万永久人物压力；
- 以统计人口替代永久人物，或按关注状态删除人物；
- 改变M13史料人口与稳定地理输入；
- 取消300秒硬超时或把部分合同通过写成全合同通过。

## 七、完成定义

代码优化、六单元矩阵、决策报告和项目级验证都有明确证据后，本任务完成。是否进入正式
后端选择只由100万完整合同结果决定，不由任务编号或10万结果自动决定。
