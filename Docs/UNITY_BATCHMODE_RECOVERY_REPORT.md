# Unity批处理恢复诊断报告

## 结论

故障已解决。它不是Unity许可证失效，也不是项目无法加载。证据确认存在四个相互独立的问题：

1. Codex工作区沙盒会阻断Unity在创建日志、启动许可证客户端之前所需的IPC或子进程初始化。同一
   `EngineSmoke`在沙盒内45秒没有日志，在沙盒外16.153秒通过。
2. 自动化宿主同时提供`Path`和`PATH`时，Windows PowerShell环境枚举会报重复键；安全入口现在只在
   自身进程内把两者折叠为一个最长值，不修改用户或系统环境。
3. 当前团结版Unity `2022.3.62f3c1`能够完成精确EditMode测试并写出有效XML，但在Test Runner触发
   的原生关闭阶段可能持续占用CPU；日志最后停在许可证IPC通道断开，120秒和180秒都未自然退出。
4. EditMode规模已从历史274项增长到当前333项。历史274项完整测试约206—208秒，284项约224秒；
   再叠加项目启动与关闭，单进程全量执行已经逼近300秒硬边界。

## 已实施恢复

- `Run-UnityTestsSafe.ps1`已拆分引擎启动、项目加载、EditMode和PlayMode模式。
- 测试过滤器、稳定结果码、非空日志检查、XML解析和JSON证据摘要已经加入。
- Unity写出完整XML后先等待15秒自然退出；仍不退出时只终止本次拥有的进程树，并在摘要中记录
  `forcedCleanupAfterResult=true`。只有XML完整且失败数为零时才可报告测试通过。
- `Run-UnityEditModeGroupsSafe.ps1`从测试源发现精确名称，默认按12组运行，并用源SHA-256指纹、预期集合
  和XML实际集合阻止漏测、重复或混用旧结果。
- 统一验证入口新增显式`UnityTestFilter`，默认覆盖范围未被静默缩减。
- 存档迁移测试从`WorldState.CurrentSchemaVersion`构造旧版本JSON，不再把当时的当前版本写死在测试
  字符串中。

- 项目加载三次通过：16.143秒、14.142秒、14.132秒。
- 沙盒内/外对照：沙盒内45秒无日志并安全终止；沙盒外引擎冒烟16.153秒通过。
- 精确迁移回归：`total=12, passed=12, failed=0`，总运行18.158秒。

  `31E754B16215E130FD610433B6DDA26CF9027C0CBFEB203AD1FF4CBBD5F3C7B4`。

  217.002、40.230、32.236、30.247秒；均低于240秒硬超时。

## 使用约束与后续优化

- Codex控制Unity时，必须通过获批的沙盒外工具调用执行安全脚本；不得在工作区沙盒内反复等待无日志
  进程。普通用户在自己的PowerShell中不需要Codex权限升级。
- Unity Editor已由用户打开时仍必须报告项目锁，不能自动关闭。
- 第9组耗时217.002秒，安全余量有限。后续可以另立工具优化任务，记录历史单测耗时并按耗时加权
  分组；在完成该优化前保留12组和240秒组内上限。
- 完整纯C#核心回归必须使用`Tools/Run-CoreTestGroupsSafe.ps1`的准备、逐组执行和聚合流程；
  单进程入口只保留兼容与定向过滤用途，不能替代完整聚合。
- 若Unity已经写出完整且零失败XML但不退出，15秒宽限后的自有进程树清理仍是允许路径，并必须在
  JSON中记录`forcedCleanupAfterResult=true`。
